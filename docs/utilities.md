# MuluOS Utilities

MuluOS-specific tools live under [`utils/`](../utils/). Each tool is a source subfolder that is copied into the ISO rootfs at build time by [`muluos/builder/utils.py`](../muluos/builder/utils.py), which runs from [`rootfs.py`](../muluos/builder/rootfs.py) right after `settings.install`.

## Per-tool layout

Make one subfolder per tool, laid out by where files land in the rootfs:

```
utils/
  disk-usage/
    usr/bin/muluos-disk-usage              # executable (auto-chmod 0755)
    usr/share/applications/muluos-disk-usage.desktop
  net-info/
    usr/bin/muluos-net-info
    usr/lib/muluos/net_info/...            # supporting Python modules
```

The builder copies every subfolder's tree over the rootfs and marks files under `usr/bin`, `usr/sbin`, and `usr/libexec/muluos` executable. **Adding a tool is just dropping a new subfolder — no further wiring needed.**

## Conventions

- **Python tools:** put the importable package under `usr/lib/muluos/<pkg>/`. The chroot hook adds `/usr/lib/muluos` to Python's path via a `.pth` file, so `import <pkg>` works regardless of the installed python3.X version.
- **Registry access:** Python tools can `import muluos_registry` to read/write config. See [`assets/registry/usr/lib/muluos/muluos_registry.py`](../assets/registry/usr/lib/muluos/muluos_registry.py) for the client API.
- **Start menu entries:** if a tool should appear in the menu, give its registry bundle the `menu.*` keys (`menu.name`, `menu.icon`, `menu.category`, etc.) rather than shipping a static `.desktop`. That keeps it consistent with the registry-driven menu generated by [`menu-sync`](../assets/registry/usr/libexec/muluos/menu-sync). A static `.desktop` under `usr/share/applications/` also works but won't be category-managed.
- **Naming:** prefix executables and desktop files with `muluos-` for consistency (e.g. `muluos-disk-usage`).
- **Executable bit:** anything outside `usr/bin` / `usr/sbin` / `usr/libexec/muluos` keeps its source permissions; set the bit in your source tree if needed.

## How it differs from other overlays

| Overlay | Builder module | Shape |
|---|---|---|
| `assets/registry/` | `registry.py` | one overlay tree |
| `assets/bundle/` | `bundle.py` | one overlay tree |
| `assets/settings/` | `settings.py` | one overlay tree |
| `utils/` | `utils.py` | **many** subfolders, each its own overlay |

`utils/` is the place for small, independent tools. Larger subsystems (with their own daemon, KIO worker, etc.) follow the single-overlay pattern under `assets/` instead.
